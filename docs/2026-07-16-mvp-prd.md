## 1. Executive summary

Binance Market Monitor is a private, read-only market intelligence service that identifies unusual market activity and market conditions worth manual review without trading automatically or presenting its output as financial advice.

The MVP will continuously scan active Binance Spot markets, apply liquidity and data-quality filters, dynamically select the strongest candidates for deeper analysis, enrich those candidates with public USD-M Futures context, and send explainable **watch alerts** to n8n for Telegram delivery.

The product is an observation and decision-support tool. It is not a trading bot, signal-selling service, portfolio manager, or profit prediction system.

The MVP must operate under the connectivity constraints verified from the current VPS:

- standard Binance Spot REST returns HTTP `451`;
- standard Binance Futures REST returns HTTP `451`;
- official Spot market-data-only REST works;
- official Spot market-data-only WebSocket works;
- Spot depth snapshots work through the market-data-only REST endpoint;
- current USD-M Futures split WebSocket routes work;
- the USD-M Futures WebSocket API can provide depth snapshots;
- Futures Open Interest is unavailable through the currently working no-auth paths and is excluded from the MVP.

## 2. Problem statement

Crypto markets contain more continuously changing instruments than a trader can evaluate manually. The largest percentage movers are often already extended, illiquid, leveraged, or driven by short-lived liquidation and promotional activity.

Alexandre needs a system that reduces the market to a manageable shortlist and answers four questions:

1. **What is moving unusually relative to its own normal behavior?**
2. **Is the movement supported by executable liquidity and actual trade flow?**
3. **Does Spot lead and is Futures context aligned with or contrary to that evidence?**
4. **Why did the system consider the movement worthy of attention?**

Existing screeners commonly expose isolated indicators or opaque scores. The monitor must instead provide evidence, data-quality status, and invalidating conditions so Alexandre can perform manual analysis.

## 3. Product principles

1. **Observation before action.** The system generates watch alerts, never orders.
2. **Liquidity before momentum.** A pair cannot qualify if it is not practically tradable.
3. **Executed flow before displayed intent.** Completed trades receive more weight than transient order-book walls.
4. **Multiple independent evidence groups.** No market alert may rely on one indicator alone.
5. **Spot-led interpretation.** Spot activity is the primary market signal; leveraged Futures data is context.
6. **Data quality is a gate.** Stale or invalid inputs suppress alerts.
7. **Explainability over complexity.** Every decision must include deterministic reason codes and thresholds.
8. **Replay before tuning.** Rules must be testable against recorded data.
9. **No geographic bypass.** The service uses only officially available endpoints from its deployment environment.
10. **No profitability claims.** MVP success is measured by operational and analytical utility, not P&L.

## 5. Goals

### G-001 — Broad market awareness

Continuously scan active and eligible Binance Spot `USDT` pairs using public market data.

### G-002 — Focused deep analysis

Dynamically perform expensive trade-flow and order-book analysis only for the strongest Stage 1 candidates and permanent baseline symbols.

### G-003 — Explainable watch-candidate detection

Generate deterministic watch alerts that state:

- what changed;
- which metrics crossed which thresholds;
- whether Spot and Futures agree;
- whether liquidity is acceptable;
- what would invalidate the evidence;
- whether any data source is degraded.

### G-004 — Safe operation

Run without Binance API keys, signed endpoints, account data, trading permissions, or order-placement code.

### G-005 — Replayability

Persist sufficient raw and normalized events to reproduce scanner decisions and evaluate false positives.

### G-006 — Reliable mobile delivery

Deliver deduplicated alerts to n8n as versioned JSON suitable for Telegram.

## 6. Non-goals

The MVP will not:

- place, modify, or cancel orders;
- connect to Binance private or account endpoints;
- require a Binance account or API key;
- calculate account position size;
- manage leverage, margin, balances, stops, or take-profit orders;
- issue `buy`, `sell`, `long`, or `short` commands;
- predict returns or provide target prices;
- claim that manipulation has been proven;
- include Futures Open Interest;
- monitor private chats or private social accounts;
- include social sentiment ingestion in the first implementation;
- provide a public SaaS or multi-user product;
- optimize for high-frequency or sub-millisecond trading;
- bypass HTTP `451` restrictions through proxies, VPNs, or alternate identities;
- use an LLM to make tick-level market decisions.

## 7. Scope and high-level architecture

```text
Official Binance public market data
              │
              ▼
       Async collectors
              │
              ▼
 Normalization + quality gates
              │
       ┌──────┴──────┐
       ▼             ▼
 Stage 1 scanner   Raw event archive
       │             │
       ▼             ▼
 Ranked candidates  Parquet / DuckDB
       │
       ▼
 Dynamic deep subscriptions
       │
       ▼
 Stage 2 features + Futures context
       │
       ▼
 Deterministic alert engine
       │
       ▼
 Dedupe + webhook → n8n → Telegram
```

The market engine owns all WebSocket state, order-book reconstruction, metrics, scoring, storage, and alert decisions. n8n receives only final low-frequency events.

## 10. Functional requirements

### 10.1 Configuration

#### FR-CONFIG-001

The application must load typed configuration from YAML or TOML plus environment variables for sensitive values.

#### FR-CONFIG-002

Configuration must include:

- eligible quote assets;
- exclusion patterns;
- permanent deep-analysis symbols;
- maximum dynamic candidates;
- Stage 1 thresholds;
- Stage 2 thresholds;
- feature windows;
- alert cooldowns;
- stale-data thresholds;
- storage paths and retention;
- webhook enablement, URL, timeout, and retry limits;
- logging level.

#### FR-CONFIG-003

The n8n webhook URL must be treated as a secret and never appear in logs, health responses, fixtures, or commits.

#### FR-CONFIG-004

Invalid configuration must fail before collectors start and return actionable validation messages.

### 10.2 Symbol universe

#### FR-UNIVERSE-001

At startup, the service must obtain current Spot symbol metadata from the working market-data-only REST endpoint.

#### FR-UNIVERSE-002

The default eligible universe must contain pairs that:

- are in trading status;
- use an allowed quote asset, initially `USDT`;
- have sufficient history for baselines;
- pass configurable minimum quote-volume and liquidity gates.

#### FR-UNIVERSE-003

The system must exclude:

- stablecoin-to-stablecoin pairs;
- leveraged-token naming patterns such as `UP`, `DOWN`, `BULL`, and `BEAR`;
- newly listed or insufficient-history symbols;
- administratively denied symbols.

#### FR-UNIVERSE-004

Symbol metadata must be refreshed periodically without restarting the service.

### 10.3 Stage 1 — broad Spot scanner

#### FR-STAGE1-001

Stage 1 must process lightweight all-market Spot data without opening full depth and trade streams for every symbol.

#### FR-STAGE1-002

Stage 1 features must include, where available:

- price return over configurable windows;
- price impulse normalized by recent volatility;
- relative quote volume;
- volume acceleration;
- realized-volatility expansion;
- trade-count acceleration;
- current bid/ask spread;
- proximity to recent high/low or range boundary;
- market-relative movement compared with BTC.

#### FR-STAGE1-003

Relative metrics must compare each pair with its own history, including time-of-day baselines where sufficient history exists.

#### FR-STAGE1-004

Stage 1 must output a ranked candidate record containing:

- symbol;
- score and score version;
- feature values;
- thresholds used;
- deterministic reason codes;
- input freshness;
- detection timestamp.

#### FR-STAGE1-005

A pair that fails the liquidity or data-quality gate cannot advance regardless of momentum score.

#### FR-STAGE1-006

Candidate ranking must use deterministic tie-breaking in this order: watch score descending, executable-liquidity score descending, symbol ascending, then detection timestamp ascending.

#### FR-STAGE1-007

Stage 1 must fail closed until the symbol has at least 15 minutes of local rolling-ticker history and samples sufficiently close to the 5-, 10-, and 15-minute cutoffs. Raw cumulative 1-hour ticker totals must never substitute for missing local-window deltas.

#### Stage 1 source map

Stage 1 must remain lightweight. Approximate broad-market features are replaced by exact candidate-level features during Stage 2.

| Feature | Broad source | Status | Minimum local history | Default stale threshold |
| --- | --- | --- | ---: | ---: |
| Latest price and sampled returns | Spot `!ticker_1h@arr` rolling ticker | Sampled approximation | 15 minutes | 5 seconds |
| Current spread | Spot all-market book ticker | Exact top of book | None | 3 seconds |
| Relative quote-volume change | Delta of 1h rolling ticker quote volume | Approximation; rolling-window expiry can affect delta | 15 minutes | 10 seconds |
| Trade-count acceleration | Delta of 1h rolling ticker trade count | Approximation; validated with Stage 2 trades | 15 minutes | 10 seconds |
| Realized-volatility expansion | Locally sampled last-price returns | Sampled approximation | 15 minutes | 5 seconds |
| Range-boundary proximity | Local sampled 15-minute price range | Approximation | 15 minutes | 5 seconds |
| BTC-relative movement | Symbol and `BTCUSDT` sampled returns | Sampled approximation | 5 minutes | 5 seconds |

No Stage 1 feature may silently require aggregate-trade or depth subscriptions for the full universe.

### 10.4 Dynamic candidate management

#### FR-CANDIDATE-001

The candidate manager must maintain permanent deep streams for baseline symbols and dynamically subscribe the highest-ranked additional candidates.

#### FR-CANDIDATE-002

Candidate promotion and eviction must use hysteresis and minimum residence time to avoid subscription churn.

#### FR-CANDIDATE-003

The manager must observe current Binance subscription and connection limits, shard connections when required, and avoid hard-coded assumptions where limits can be discovered or configured.

#### FR-CANDIDATE-004

A newly promoted candidate must remain in warm-up state until its required windows and order book are valid. Warm-up candidates cannot emit market alerts.

### 10.5 Spot deep analysis

#### FR-SPOT-001

For active candidates, ingest:

- aggregate trades;
- best bid and ask;
- incremental depth;
- 1-minute klines;
- any additional public stream explicitly approved in configuration.

#### FR-SPOT-002

Compute:

- aggressive buy and sell notional;
- Spot CVD approximation;
- CVD slope and divergence;
- spread in basis points;
- depth within configurable basis-point bands;
- estimated slippage for configured reference notionals;
- order-book imbalance;
- depth collapse and recovery;
- breakout, retest, rejection, and liquidity-sweep structure.

#### FR-SPOT-003

CVD must be labeled as an approximation inferred from public maker-side trade fields, not as trader intent.

### 10.6 Futures context

#### FR-FUTURES-001

USD-M Futures streams must use Binance's current split routing:

- regular direct stream: `wss://fstream.binance.com/market/ws/<stream>`;
- regular combined streams: `wss://fstream.binance.com/market/stream?streams=<stream1>/<stream2>`;
- high-frequency direct stream: `wss://fstream.binance.com/public/ws/<stream>`;
- high-frequency combined streams: `wss://fstream.binance.com/public/stream?streams=<stream1>/<stream2>`.

Regular market data includes aggregate trades, mark price, klines, and force orders. High-frequency public data includes depth and book-ticker updates. The implementation must not omit the `/ws/` or `/stream?streams=` segment and must not use the retired pre-April-2026 Futures stream paths.

#### FR-FUTURES-002

For deep candidates with a mapped perpetual contract, ingest where available:

- aggregate trades;
- mark price;
- index-price and current-funding fields carried by the mark-price stream;
- book ticker;
- incremental depth;
- liquidation/force-order events.

#### FR-FUTURES-003

Compute:

- Futures CVD approximation;
- Spot/Futures CVD divergence;
- Futures mark-to-Spot-mid basis;
- funding context relative to locally collected history;
- liquidation count, notional, direction, and velocity;
- Futures depth and spread state.

#### FR-FUTURES-004

The MVP must not compute, infer, or simulate Open Interest. UI and payloads must report `open_interest_available: false`.

#### FR-FUTURES-005

Unavailable Futures data must lower evidence confidence and attach a reason code. It must not stop a healthy Spot-only scanner.

### 10.7 Local order books

#### FR-BOOK-001

Spot and Futures books must be reconstructed independently from an official depth snapshot plus incremental depth events.

#### FR-BOOK-002

Initialization sequence:

1. open and buffer depth-diff events;
2. request the corresponding official snapshot;
3. discard buffered updates older than the snapshot update ID;
4. apply the first event only when it correctly bridges the snapshot;
5. apply subsequent events in strict documented sequence.

For Spot, the first applicable event must satisfy `U <= snapshot.lastUpdateId + 1 <= u`. After initialization, an event with `u < local_last_update_id + 1` is obsolete and ignored; an event with `U > local_last_update_id + 1` is a gap and forces invalidation and resynchronization.

For Futures, the first applicable event must satisfy `U <= snapshot.lastUpdateId <= u`. After initialization, each event's `pu` must equal the prior applied event's `u`; otherwise the book is invalidated and resynchronized.

#### FR-BOOK-003

For Futures events containing `pu`, each event's previous final update ID must match the prior applied event's final update ID.

#### FR-BOOK-004

A sequence gap, crossed book, malformed update, stale stream, or impossible state must:

- mark the book invalid;
- suppress dependent alerts;
- clear or quarantine partial state;
- initiate a bounded resynchronization.

#### FR-BOOK-005

Price and quantity must use `Decimal`, integer ticks, or original decimal strings. Binary floating point must not be used as the canonical representation.

#### FR-BOOK-006

A zero quantity removes a price level. Removing an unknown level is valid and must not crash the service.

#### FR-BOOK-007

Each book must expose:

- state: `warming`, `valid`, `stale`, `invalid`, or `resync_pending`;
- last update ID;
- exchange timestamp;
- local receive timestamp;
- age;
- best bid and ask;
- spread;
- selected depth bands.

#### FR-BOOK-008

Spot REST snapshots may request up to the documented 5,000 levels per side. USD-M Futures WebSocket API snapshots must use a documented limit no greater than 1,000. Depth outside the initial snapshot's covered price range is incomplete until populated by updates and must not be presented as complete liquidity.

#### FR-BOOK-009

Liquidity metrics may only use a configured basis-point band fully contained within the currently known snapshot range. Metrics outside that range must be marked unavailable.

### 10.8 Feature engine and market regimes

#### FR-FEATURE-001

Feature functions must be deterministic, side-effect free where practical, and independent from connector I/O.

#### FR-FEATURE-002

The engine must maintain configurable rolling windows including 1 minute, 5 minutes, 15 minutes, and 1 hour where sufficient data exists.

#### FR-FEATURE-003

Market features must distinguish:

- Spot-led participation;
- Futures-led leveraged movement;
- liquidation-driven movement;
- volatility expansion;
- liquidity deterioration;
- failed breakout or rapid reversion;
- degraded or incomplete evidence.

### 10.9 Alert engine

#### FR-ALERT-001

A market watch alert must require multiple independent factors. Price movement or a single indicator alone is insufficient. When Futures context is unavailable, Spot-only confirmation must include both a Stage 1 market anomaly and directionally aligned fresh Spot CVD; liquidity or range structure alone cannot replace aligned flow evidence. Aggregate trades, rolling ticker data, and book ticker data outside their configured freshness thresholds must suppress dependent alerts.

#### FR-ALERT-002

Initial alert taxonomy:

1. `spot_led_momentum_watch`
2. `breakout_retest_watch`
3. `liquidity_sweep_recovery_watch`
4. `futures_led_divergence_warning`
5. `liquidation_cascade_warning`
6. `liquidity_deterioration_warning`
7. `data_quality_warning`
8. `system_health_alert`

#### FR-ALERT-003

Every alert must contain:

- schema version;
- unique alert ID;
- dedupe key;
- symbol and market;
- alert type and severity;
- watch score and score version;
- evidence confidence;
- deterministic reason codes;
- feature values and thresholds used;
- data-source and order-book health;
- Spot/Futures context availability;
- invalidating conditions;
- UTC timestamps;
- disclaimer.

#### FR-ALERT-004

The watch score is a ranking aid, not a probability of profit. This must be explicit in documentation and alert templates.

#### FR-ALERT-005

Cooldown and deduplication must operate per symbol and alert regime. A continuation event may be emitted only when the evidence materially changes after the configured interval.

#### FR-ALERT-006

Market alerts must be suppressed when required data is stale, the local book is invalid, storage backpressure threatens correctness, or the candidate has not completed warm-up.

#### FR-ALERT-007

Alert text must avoid explicit or implied execution instructions, including `entry`, `target`, `stop`, `take profit`, `trade now`, `confirmed trade`, `high-probability setup`, or equivalent language. Technical invalidation describes when evidence no longer holds; it is not a stop-loss instruction.

### 10.10 Webhook and Telegram delivery

#### FR-WEBHOOK-001

The service must POST versioned JSON alerts to a configured n8n webhook.

#### FR-WEBHOOK-002

Webhook delivery must include:

- bounded timeout;
- bounded exponential retry with jitter;
- idempotency key;
- locally persisted delivery result;
- no blocking of market ingestion.

#### FR-WEBHOOK-003

Webhook-disabled mode must allow full local monitoring and replay.

#### FR-WEBHOOK-004

n8n is responsible for Telegram routing and may format the machine payload into a concise message. Tick-level data must never be sent to n8n.

### 10.11 Storage

#### FR-STORAGE-001

The MVP must store append-oriented raw and normalized data as Parquet compressed with Zstandard.

#### FR-STORAGE-002

Datasets must be partitioned by appropriate combinations of:

- date;
- hour;
- market;
- symbol;
- stream type.

#### FR-STORAGE-003

DuckDB must expose queryable views or tables for:

- raw market events;
- normalized trades;
- depth snapshots and diffs;
- top-of-book metrics;
- Stage 1 candidates;
- Stage 2 decisions;
- alerts;
- manual alert reviews;
- connector and data-quality status.

#### FR-STORAGE-004

Storage writers must batch events from bounded queues and flush cleanly during graceful shutdown.

#### FR-STORAGE-005

A storage failure must degrade readiness, trigger bounded retry, and avoid unbounded memory growth.

### 10.12 Replay

#### FR-REPLAY-001

The service must replay recorded event windows without live Binance access.

#### FR-REPLAY-002

The same ordered input and configuration must produce content-equivalent features, candidate decisions, reason codes, and alerts.

#### FR-REPLAY-003

Replay must support:

- fast deterministic execution;
- optional event-time-speed execution;
- synthetic disconnects and sequence gaps;
- corrupted-event fixtures;
- comparison of threshold versions.

#### FR-REPLAY-004

Historical evaluation must report descriptive post-alert market behavior and false-positive review data. It must not report simulated profitability unless a separately reviewed backtesting specification is approved.

### 10.13 Health and internal API

The MVP must expose a read-only FastAPI service.

Required endpoints:

```text
GET /health/live
GET /health/ready
GET /health/binance
GET /metrics/summary
GET /candidates/current
GET /books/{market}/{symbol}
GET /alerts/recent
```

Health responses must never expose webhook URLs or other secrets.

#### FR-API-001

The FastAPI service must bind to `127.0.0.1` by default. If exposed beyond localhost, it must be protected by an authenticated reverse proxy or explicit network allowlist. An unauthenticated public deployment fails acceptance.

### 10.14 Machine-enforced data contracts

#### FR-CONTRACT-001

Versioned Pydantic models must define, validate, and generate JSON Schema for:

- normalized trade events;
- normalized depth diffs and snapshots;
- local-book state;
- Stage 1 candidates;
- Stage 2 decisions;
- alert payloads;
- connector health;
- manual alert reviews.

#### FR-CONTRACT-002

Canonical prices, quantities, notionals, and CVD values must be decimal strings or fixed-point encoded values. Percentages and basis-point display metrics may use JSON numbers.

#### FR-CONTRACT-003

Contracts must distinguish, where available:

- exchange event time;
- exchange transaction time;
- local receive time;
- feature calculation time;
- candidate detection time;
- alert emission time.

All timestamps must use UTC and document whether they are ISO 8601 strings or epoch milliseconds.

### 10.15 Backpressure and correctness

#### FR-BACKPRESSURE-001

Each stream class must have a bounded queue and an explicit overflow policy.

- **Depth diff:** never drop and continue as valid. Overflow invalidates every affected local book, increments a reason-coded metric, and triggers bounded resynchronization.
- **Trade flow:** shedding is allowed only with an explicit loss marker; flow-dependent alerts remain suppressed until the full configured feature window is rebuilt.
- **Ticker and book ticker:** latest-value coalescing by symbol is allowed and must increment a coalescing metric.
- **Storage:** crossing the critical queue limit fails readiness and suppresses market alerts. If the queue does not recover within the configured grace period, the service performs a controlled shutdown rather than grow memory without bound.
- **Webhook:** delivery backlog never blocks ingestion; exceeding its limit persists failure state and suppresses additional duplicate deliveries.

#### FR-BACKPRESSURE-002

Queue-overflow fixtures must prove invalidation, suppression, and recovery behavior. No overflow path may leave a plausible but corrupted book marked valid.

### 10.16 Manual alert review

#### FR-REVIEW-001

The system must support a stored manual review record with:

- `alert_id`;
- `review_status`: `useful`, `noisy`, `late`, `misleading`, or `unreviewed`;
- `reviewed_at`;
- `review_notes`;
- optional reason categories.

Reviews are analytical feedback only and must not mutate historical scanner inputs or decisions.

## 13. Nonfunctional requirements

### 13.1 Reliability

- Automatic WebSocket reconnect with jittered exponential backoff.
- Planned reconnect before documented connection expiration.
- Automatic resubscription.
- Per-symbol book resynchronization.
- Graceful shutdown with bounded queue flush.
- No silent event dropping.
- Depth events required for book continuity must never be dropped silently.

### 13.2 Performance

Initial engineering targets:

- support at least 20 simultaneous deep-analysis symbols on the current VPS;
- process the full eligible Spot universe through Stage 1 aggregate streams;
- p95 event-to-feature latency below 2 seconds under normal MVP load;
- health API p95 response below 500 ms under normal load;
- no unbounded queue or memory growth during a 24-hour pilot.

These are service-quality targets, not trading-latency guarantees.

### 13.3 Pilot operational limits

Initial defaults are acceptance targets, not immutable production values:

| Control | Initial pilot limit |
| --- | ---: |
| Per-symbol depth-diff queue | 2,000 events; overflow invalidates and resynchronizes |
| Trade queue per connection shard | 10,000 events; overflow adds a loss marker and rebuilds flow windows |
| Storage queue | 50,000 events; critical state suppresses alerts |
| Storage critical-state grace period | 60 seconds before controlled shutdown |
| Webhook retry backlog | 100 alerts |
| Depth/book-ticker stale age | 3 seconds |
| Candidate aggregate-trade stale age | 10 seconds |
| Futures mark-price stale age | 5 seconds |
| Storage flush target | 5 seconds; readiness fails above 30 seconds |
| Excessive reconnect threshold | More than 10 reconnects per connector in 10 minutes |
| Excessive book-resync threshold | More than 5 attempts per symbol in 10 minutes; quarantine for 10 minutes |
| Process RSS budget | 1 GiB during the controlled pilot |
| Normal-condition alert budget | At most 20 market watch alerts per UTC day |
| Repeated symbol/regime budget | At most 2 alerts in a rolling 6-hour window unless evidence materially changes |

Any changed limit must be versioned with the configuration used for replay and pilot evaluation.

### 13.4 Security

- Public read-only market data only.
- No Binance API key or account identifier.
- No signed endpoint support.
- No order models, trading clients, or execution methods.
- No proxy rotation or geo-bypass logic.
- Webhook secret supplied only at runtime.
- Structured secret redaction in logs.
- Outbound-only collector network access where operationally practical.
- Repository remains private until explicitly reviewed for publication.
- FastAPI binds to `127.0.0.1` by default and may not be publicly reachable without authentication or an allowlist.

### 13.5 Maintainability

- Python 3.12 or newer.
- Fully typed internal contracts.
- Connector interfaces separated from normalized domain models.
- Deterministic scanner functions separated from I/O.
- Dependency versions locked.
- Conventional commits.
- Branch → PR → manual approval workflow.

### 13.6 Observability

Structured logs and metrics must expose:

- connector state;
- last-event age;
- reconnect count;
- events received and rejected;
- queue depth and dropped-event count;
- local-book state;
- gap and resync counts;
- Stage 1 candidates;
- Stage 2 decisions;
- alerts emitted and suppressed;
- webhook success and failure;
- storage rows and flush duration.

A single readiness response must explain whether the service is healthy, degraded, stale, or blocked by storage.

## 14. Failure modes and required behavior

| Failure | Required behavior |
| --- | --- |
| Standard REST returns HTTP `451` | Record expected geographic restriction; never retry through a bypass; continue approved sources |
| Spot market-data REST unavailable | Keep live streams if healthy; disable snapshot-dependent features and suppress affected book alerts |
| WebSocket disconnect | Mark stream stale, reconnect with backoff, resubscribe, warm required windows |
| Depth sequence gap | Stop applying updates, invalidate book, resnapshot and resynchronize |
| Crossed or impossible book | Quarantine state, suppress alerts, trigger resync |
| Futures context unavailable | Continue Spot analysis with lower evidence confidence and explicit reason code |
| Snapshot timeout | Set `resync_pending`, retry within rate limits, suppress dependent alerts |
| Storage failure | Fail readiness, retry boundedly, prevent unbounded queue growth |
| Webhook failure | Persist failed delivery, retry boundedly, keep ingestion running |
| Backpressure | Apply documented policy; never silently corrupt book sequence |
| Clock skew | Preserve exchange and receive times separately; expose excessive skew |
| Unknown schema/event | Count and store safely where possible; do not crash ingestion |

### 15.1 Unit tests

- decimal/fixed-point price handling;

### 15.2 Integration tests

- mock Spot WebSocket ingestion;
- mock Futures `/market` and `/public` streams;
- mock Spot depth snapshot;
- mock Futures WebSocket API depth snapshot;
- reconnect and resubscribe;
- Parquet write and DuckDB query;
- FastAPI health transitions;
- webhook success, timeout, retry, and failure persistence.

### 15.3 Replay tests

- snapshot plus ordered diffs produces deterministic top-of-book;
- duplicate events do not corrupt state;
- missing update triggers resynchronization;
- corrupted payload increments invalid-event metrics and does not stop replay;
- identical input and configuration produce content-equivalent candidate and alert outputs;
- stale data suppresses market alerts;
- depth-queue overflow invalidates and resynchronizes the affected book;
- trade-queue shedding marks loss and suppresses flow-dependent alerts until recovery.

### 15.4 Network tests

Live Binance tests must be explicitly opt-in and skipped in default CI. CI must run offline and require no API keys. The repository must include `scripts/check_connectivity.py` to reproduce the approved endpoint smoke checks and emit a secret-free result.

## 16. Acceptance criteria

### AC-001 — Repository and safety boundary

- The repository is private.
- README links to this PRD.
- No account, trading, signed-endpoint, or API-key code exists.
- No direct feature commits are made to `main`.

### AC-002 — Approved data access

- Spot metadata, backfill, and snapshots use `data-api.binance.vision`.
- Spot live data uses `data-stream.binance.vision`.
- Futures live data uses the exact `/market/ws/` or `/market/stream?streams=` and `/public/ws/` or `/public/stream?streams=` forms.
- Futures depth snapshots use the public WebSocket API `depth` method.
- Standard endpoints returning HTTP `451` are not runtime dependencies.
- The opt-in connectivity script reproduces the expected route status without credentials.

### AC-003 — Broad scanner

- Stage 1 scans the configured eligible Spot universe.
- It emits a ranked candidate set with features, thresholds, reason codes, and freshness.
- Illiquid or stale symbols cannot advance.

### AC-004 — Deep scanner

- Permanent baseline symbols and dynamic candidates receive deep streams.
- Candidate warm-up prevents premature alerts.
- Stage 2 uses multiple independent evidence groups.

### AC-005 — Local books

- Spot and Futures books initialize from snapshots and apply documented sequence rules.
- Synthetic gap and crossed-book tests trigger invalidation and resynchronization.
- Alerts dependent on an invalid book are suppressed.

### AC-006 — Futures context

- Current funding, basis, Futures flow, depth, and liquidation context are supported where available.
- Missing context degrades evidence confidence safely.
- Open Interest is absent and explicitly reported unavailable.

### AC-007 — Explainable alerts

- Every market alert includes reason codes, metric values, thresholds, evidence confidence, data quality, invalidation, and disclaimer.
- No market alert is generated from one indicator alone.
- No alert instructs the user to buy, sell, long, short, or use leverage.
- No alert implies execution through `entry`, `target`, `stop`, `take profit`, `trade now`, `confirmed trade`, or `high-probability setup` language.

### AC-008 — n8n delivery

- Alerts POST as versioned JSON to a test webhook.
- Idempotency, cooldown, timeout, retry, and failure persistence are verified.
- Webhook failure does not block ingestion.

### AC-009 — Storage and replay

- Raw/normalized Parquet is queryable through DuckDB.
- A recorded fixture can reproduce the expected candidate and alert outputs offline.
- Restarting does not corrupt existing datasets.
- Pydantic contracts generate versioned JSON Schema for every required event, decision, health, alert, and review record.
- Manual review fields persist without altering historical decisions.

### AC-010 — Operations

- Required health endpoints are implemented.
- Health reflects live, ready, degraded, stale, and storage-failure states.
- Logs expose reconnects, gaps, resyncs, alert suppression, and webhook failures without exposing secrets.
- FastAPI binds to localhost by default; an unauthenticated public exposure fails acceptance.

### AC-011 — Pilot stability

- The service completes a controlled 24-hour run on the intended VPS without an unhandled crash.
- Process RSS remains within the initial 1 GiB budget and all queues remain within the limits in Section 13.3.
- Reconnect, resync, stale-age, storage-lag, and webhook-backlog limits in Section 13.3 are enforced and observable.
- Every reconnect, gap, resync, and dropped event is observable.
- Queue-overflow tests prove invalidation or explicit loss handling, never silent continuation.

## 17. Success metrics

### 17.1 Technical

- 24-hour controlled run completes without unhandled process failure.
- No alert is emitted from stale required data.
- Every order-book sequence gap results in invalidation or resync, never silent continuation.
- Offline test and replay suites pass without network access.
- Parquet output remains queryable after restart.
- Webhook delivery failures are persisted and do not stop ingestion.

### 17.2 Product utility

- Every alert can be understood from the Telegram message in approximately 30 seconds.
- Every market alert exposes its supporting evidence and invalidating conditions.
- Under normal pilot conditions, market watch alerts remain within the 20-per-day budget and repeated symbol/regime alerts remain within the rolling 6-hour budget.
- Alexandre can persistently classify each reviewed alert as useful, noisy, late, or misleading during the pilot, with timestamp, notes, and optional reason categories.
- Pilot review produces enough evidence to set future precision and alert-volume targets.

MVP success is not measured by simulated or realized trading profit.

## 18. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Binance changes endpoints or schemas | Connector isolation, schema versioning, contract tests, health alerts |
| Additional regional restrictions | No bypass; degrade safely; reassess approved sources |
| Futures interpretation weakened without OI | Explicit limitation; Spot-led design; no inferred OI |
| Manipulation creates false positives | Liquidity gates, cross-market evidence, future cross-exchange confirmation |
| Order-book corruption appears plausible | Strict update-ID validation, crossed-book detection, replay fixtures |
| Excess alert volume | Hysteresis, multi-factor gates, cooldown, dedupe, continuation rules |
| Overfitted thresholds | Historical baselines, versioned configs, replay, out-of-sample review |
| Storage growth | Partitioning, compression, retention policy, aggregated long-term datasets |
| Webhook secret leaks | Runtime secret, redaction, no URL in logs or health responses |
| User interprets alert as advice | Neutral wording, evidence, invalidation, mandatory disclaimer |
| n8n becomes a throughput bottleneck | Send only final alerts; never route tick events through n8n |
